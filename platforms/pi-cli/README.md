# Pi CLI adapter

The root launcher also accepts `--scenario PATH [--print] [--model ALIAS]
[--provider ID]`. A scenario is validated Markdown passed verbatim to one ordinary
Pi session. Version 2 `pi-agents` configuration selects a roster role and model
bindings per workflow, including Financial Insights; it never defaults another
workflow to Dev Coder. Both the profile and selected workflow must register
`pi-agents`. See the [command contract](../../ai-commands/system/pi-agents/pi-agents.command.md)
for validation, configuration and bounded noninteractive execution.

Scenario launches disable Pi's automatic context-file, skill and prompt-template
loading and project approval/loading using `--no-context-files --no-skills
--no-prompt-templates --no-approve`. The supplied prompt explicitly limits the
session to its scenario and authorized folders. Ordinary role previews retain
their existing loading behavior.
Scenario mode uses a concise system prompt and the `read,bash` tool allowlist to
preserve authorized file inspection and processing within a smaller token budget.

`pi-cli` is the AI Fleas platform ID for the Pi terminal harness. The selected work profile still owns workflow and project authorization, model bindings, and platform selection. Pi's `PI_CODING_AGENT_DIR` names a directory of harness configuration; its JSON files are not another work profile and do not establish an agent identity.

| Portable concept | Pi CLI realization |
| --- | --- |
| Logical agent | One configured role in the selected workflow roster; scenario sessions load only scope and model settings |
| Runtime configuration | A project and role specific `PI_CODING_AGENT_DIR` generated by `pi-agents prepare` |
| Agent instance | One Pi conversation/session started with that directory and the authorized project as working directory |
| Instance ID | Pi's exact, immutable session ID; the directory path and session file name are not substitutes |
| Runtime scope | Exact work profile, workflow, logical project, and authorized repository root |
| Activate/deactivate | A lifecycle controller's verified binding and routing state for that exact session |
| Send/receive | Controller delivery to the bound session through Pi's real input lifecycle |

The last three mappings describe the required managed adapter contract in [initialization](agents/initialization.md). The current command implements configuration preparation, not that lifecycle. Running `pi` directly with a prepared directory starts an ordinary Pi session. It must not claim workflow Coder readiness or receive Router work merely because its instructions name the role.

From the repository checkout, `./ai-fleas` offers an interactive profile → workflow → platform → project choice. The explicit form is `./ai-fleas --profile ID --workflow ID --project ID --platform pi-cli`. Its Pi path runs `pi-agents check` and `prepare`, then opens the configured ordinary session. With `--scenario`, preparation uses a separate scenario directory and excludes role processing instructions and lifecycle commands. The launcher's platform choice applies to that invocation; it does not rewrite workflow YAML or turn the session into a managed agent. Other platform launch paths are pending.

The launcher offers valid profiles from this repository's public `ai-profile/` catalog, the optional sibling `../ai-fleas-platform/ai-profile/` catalog, and an optional home pointer at `~/.config/ai-fleas/config-bundle-root`. An absent private sibling is silently skipped. Interactive duplicate IDs are labeled by source; noninteractive duplicate IDs require an explicit source. `--config-bundle-root PATH` or `AI_CONFIG_BUNDLE_ROOT` exclusively selects one catalog or profile bundle. Discovery does not grant identity or workflow authority. The selected profile must register `pi-cli` as available and `pi-agents` as a command for the selected workflow.

The portable workflow roster applies regardless of platform. Selecting `pi-cli` in a work profile is a prerequisite for managed Pi agents; it does not by itself initialize the roster. The current Pi adapter prepares configuration and launches ordinary sessions. Full roster creation, communication, scheduling, continuity, independent review, and human gates remain unsupported until each required capability has a concrete implementation and verification path. A missing capability blocks the dependent workflow stage instead of merging roles into one Pi session.
