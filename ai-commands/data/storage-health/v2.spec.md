# storage-health v2 — UI-ready capability

## Goal

Deliver storage-health v2 as a non-technical-user-friendly storage capability with a structured contract suitable for the existing AI Fleas Electron/browser UI pattern.

v1 remains the working CLI. v2 must preserve deterministic CLI/agent operation while adding a UI-ready boundary.

## Product principle

Users should answer “what do I want this storage to do?” rather than understand SMART attributes, rotational latency, blkid, wipefs, or /dev/sdX.

Technical evidence remains available as details.

## Architecture

```mermaid
flowchart LR
    L[Linux storage tools] --> C[storage-health core]
    C --> J[Stable structured JSON]
    J --> H[Human CLI]
    J --> U[Angular UI]\n    U --> E[Electron / browser shell]
    J --> A[Agents / automation]
```

The UI must consume structured output. It must not parse human terminal prose.

## v2 structured contract

Each discovered device should expose:
- stable runtime identity
- friendly model/name
- capacity bytes + friendly capacity
- transport and medium type
- physical health: healthy/warn/fail/unknown
- filesystem/content state
- SMART test state: never/running/passed/failed/aborted/unknown
- progress/remaining when available
- started-at and estimated completion when known
- AI suitability by workload
- plain-language recommendation
- next actions
- optional technical evidence

Stable actions:
- discover
- qualify
- start-test
- test-status
- test-history

All structured actions require a version field, e.g. `schema_version: 2`.

## Human terminology

Default surfaces should prefer:
- “AI memory — Good”
- “Documents & knowledge — Good”
- “Vector search — May be slow”
- “Active models — Use faster storage”
- “Health test — Running”
- “Ready to initialize”

Technical terms belong behind details.

## UI technology standard

All AI Fleas product UI is Angular. Storage-health v2 MUST use Angular components/services and the existing Angular + Electron/browser application pattern. Do not introduce jQuery, ad-hoc DOM manipulation, or a separate UI framework.

Electron is the desktop shell; Angular owns the renderer/application UI. The same Angular surface should remain browser-compatible where the launcher architecture permits it.

Prefer shared AI Fleas UI components, layout, status semantics, and service patterns over command-specific UI conventions.

## UI deliverable

Follow the existing AI Fleas command UI pattern: optional command launcher/UI adapter, Angular renderer inside the existing Electron/browser-compatible shell, and shared structured command contract.

Initial storage screen:

```text
Storage for your AI

We found 2 unused drives.

10 TB HDD                 HEALTHY
Good for:
✓ AI memory
✓ Documents & knowledge
✓ Model archive
△ Vector search
✕ Active model workspace

3 TB HDD                  TESTING
Long health test · ~10% complete
Expected completion ~6:20 PM

[View details]
```

Primary actions:
- Check storage
- Test drive health
- Recommend a use
- View test/history
- View technical details

No formatting, partitioning, mounting, or binding in the first UI version.

## Acceptance

Use a second real HDD as the acceptance path after v1 qualification of the first drive:
1. UI/structured discovery finds it.
2. Friendly capacity/model are shown.
3. Existing SMART history is shown before offering a test.
4. Long-test duration is estimated before confirmation.
5. Running status can be refreshed after reconnect.
6. Completion becomes a friendly pass/fail assessment.
7. AI workload recommendations match CLI evidence.
8. Raw evidence is available but not the default surface.
