# AI Local Provider Installer Notes

## ARM64 GB10 CUDA provisioning

* **What happened:** The installer originally accepted only AMD64 and always installed Ubuntu's `nvidia-cuda-toolkit`. On Ubuntu 24.04 ARM64, that package candidate is CUDA 12.0 and does not support the GB10's compute capability 12.1.
* **Root cause:** The installer treated the distribution toolkit as suitable on every architecture and did not use the already installed CUDA toolkit path or set an explicit CUDA architecture for CMake.
* **Fix:** ARM64 presets may declare `runtime.cuda_toolkit_path`, `runtime.cuda_toolkit_major_version`, and `runtime.cuda_architectures`. The provisioner uses that toolkit from `PATH`, checks its major version, and passes `CMAKE_CUDA_ARCHITECTURES` to CMake. The Qwen3.8 GB10 preset uses `/usr/local/cuda`, CUDA 13, and architecture `121`; AMD64 presets continue using the distribution toolkit path.
* **Avoid:** Do not install the Ubuntu ARM64 `nvidia-cuda-toolkit` candidate for GB10 builds. Do not rely on CMake autodetecting SM 121.
* **Verification:** The GX10 preflight identified Ubuntu 24.04 ARM64, NVIDIA GB10 compute capability 12.1, CUDA 13.0.3 at `/usr/local/cuda/bin/nvcc`, and approximately 252 GiB free on `/`. The installer compares the detected remote architecture to the preset before provisioning; the provisioner checks the declared CUDA major version and sets the explicit architecture. Remote installation must still verify the build and provider inference before reporting success.

## Switching from an active user model service

* **What happened:** Replacing the selected model can require stopping an active per-user systemd model service so its GPU memory is released.
* **Root cause:** A system service cannot safely infer which user's service manager to control from a fixed username, and stopping the existing model too early can leave the machine without a working model if installation fails.
* **Fix:** An explicit `--switch-from-user-service UNIT` option identifies the unit. The provisioner uses `SUDO_USER` and that user's `/run/user/<uid>/bus`, validates that the requested unit is active, and stops it only immediately before starting the new provider. An exit trap restarts the old unit if provider startup or inference verification fails; after successful health and inference checks, the old unit remains stopped.
* **Avoid:** Do not hard-code a username, stop unrelated services, or stop the old unit before the new model and service unit are ready.
* **Verification:** Review the command path to confirm the option is passed literally as one argument, the unit name is constrained to a `.service` name, and rollback is armed only after a successful stop. Runtime verification must confirm the new provider's health and inference, plus the old user unit's final state.

## General-purpose model install and switch flow

* **What happened:** A successful local provider install can still leave the user's API serving the old model, because a separate user gateway advertises and routes model IDs independently of the provider service.
* **Root cause:** The installer verifies the provider's own health and inference but does not discover or edit arbitrary gateways or private model-mode registries.
* **How to do it:** Read the target scope's `AGENTS.md` first. Run `preflight` for the selected preset and storage volume; confirm OS/architecture, GPU, CUDA toolkit and explicit CUDA architecture, free disk, SSH/sudo, and the currently active service. Use a preset that pins the model revision, every shard's exact byte size and SHA256, runtime revision, service unit, port, and hardware flags. Run installer `--dry-run` when the CLI supports it, then install with an explicit `--switch-from-user-service UNIT`. Keep the existing model files and unit. After provider health and inference succeed, inspect the actual API gateway's route table and health endpoint; add the new API alias pointing to the provider's listening port if needed, restart the gateway, and verify its model list and a real completion through that gateway. Preserve the previous route and service details for rollback.
* **Avoid:** Do not infer that “downloaded” means “switched.” Do not stop the existing model before the new model has downloaded and verified. Do not edit an external/private profile registry or gateway repository unless that write scope is explicitly authorized. If gateway update or end-to-end verification fails, stop the new provider, restore the old model service and gateway route, and verify the prior endpoint.
* **GB10 ARM64 note:** NVIDIA GB10 is SM 12.1; Ubuntu 24.04 ARM64's distro CUDA package may be too old. Use the installed supported toolkit, validate its version, and pass explicit CUDA architecture `121` rather than relying on autodetection.
* **Verification:** Record shard checksum/size validation, new service health and completion, old service state, gateway `/v1/models`, and one gateway-routed completion. Treat each layer separately so the result shows whether download, load, or switch failed.
* **Checksum mismatch:** When a shard download has the expected size but fails SHA256, compare the computed digest against the exact pinned Hugging Face file metadata. A transposed character in the preset checksum caused repeated safe failures even though direct downloads were valid; correct the manifest only from authoritative pinned metadata, then retry with verification enabled.
* **Role routing and benchmark scope:** Dev's Command Runner owns registered install/switch commands; Coder owns installer and preset implementation. Resolve the selected profile's effective model binding before claiming this work is Luna-capable; a public `profile-default` binding is not evidence of Luna. The existing local-image benchmark only covers image-generation candidates. For text models, distinguish smoke inference and endpoint latency from a formal throughput benchmark, which needs a separately defined prompt/token/repeat/memory protocol.
* **Managed gateway:** A preset may declare a `gateway` with its listening port, bind address, and service name. In that case the installer deploys the repository's fixed-upstream gateway, replaces an explicitly named active user gateway only after the provider passes inference, then verifies gateway health and a routed completion. On gateway failure it stops the managed gateway and restarts the named user gateway. Do not mutate a private gateway implementation or its hard-coded route map from this command.
* **Probe parsing:** Remote probe output can contain repeated records when a transport retries or wraps a probe. For scalar facts such as `arch`, take the first matching record (`awk ...; exit`) before validating it. Passing every matching line into a single comparison produces a newline-containing value and falsely rejects a supported host.
