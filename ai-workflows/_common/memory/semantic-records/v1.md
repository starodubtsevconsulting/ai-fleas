# Memory semantic record contract — v1

## Purpose

Define portable semantics for durable memory records independently of the physical storage adapter.

Google Drive, Synology/Obsidian, local files, a database, or a future fact-memory/index service may store the records differently. The semantic fields should evolve more slowly than the storage medium so memory can migrate without losing meaning.

This contract complements the Zettelkasten-inspired knowledge method and the provider-neutral `permanent-memory` command. It does not require every memory object to be a Zettelkasten concept.

## Record classes

Useful durable records may include:

- `goal` — a human-owned durable outcome.
- `decision` — a decision, rationale, evidence, and review trigger.
- `hypothesis` — a claim being tested.
- `opportunity` — a possible future allocation or collaboration.
- `asset` — an owned/reusable capability or resource.
- `resource` — an external place, service, website, community, facility, course, tool, or other reusable means toward a goal.
- `reference` — durable source/reference material.
- `concept` — durable knowledge.
- `event` / `evidence` — dated observations useful for later reasoning.

Storage adapters may add provider-specific metadata but should preserve these semantic distinctions.

## Common metadata

Use fields when they add retrieval or governance value; do not populate meaningless fields merely for schema completeness.

```yaml
id: stable-human-readable-id
type: resource
subtype: language-learning
status: active
memory-tier: permanent

name: Human-readable name
summary: Short durable description

purpose:
  - why-this-is-useful

goal-alignment:
  - stable-goal-id

strategic-paths: []
relationships: []
provenance:
  source: human-report
  source-uri: null
  captured-at: 2026-09-18
  confidence: direct

freshness:
  policy: recheck-before-use
  dynamic-fields:
    - schedule
    - price
    - availability

retrieval:
  topics:
    - french
    - montreal
  tags:
    - "#resource"
    - "#place"
    - "#french"
  aliases: []

review:
  last-reviewed: 2026-09-18
  trigger: null
```

## Goal alignment

For Governor memory, reusable resources should normally explain which human-owned goal or capability they support and how.

Do not infer a new goal merely because a resource exists. `goal-alignment` references an already accepted goal or explicitly records `none`/unknown.

Alignment is semantic metadata, not a ranking score. One object may support multiple goals.

Example:

```yaml
id: maison-de-lamitie
type: resource
subtype: language-learning
status: candidate
name: Maison de l'amitié
purpose:
  - in-person-french-conversation
goal-alignment:
  - functional-french-integration
freshness:
  policy: recheck-before-planning
  dynamic-fields: [schedule, price, registration, eligibility]
retrieval:
  topics: [french, language-learning, montreal, conversation]
  tags: ["#resource", "#place", "#french", "#montreal"]
```

## Dynamic facts and freshness

Do not turn changing external facts into timeless memory.

Opening hours, schedules, prices, availability, eligibility rules, addresses, contact details, and similar values should carry a freshness policy. The durable record may preserve the authoritative source and last-known value, but consumers should recheck fields marked dynamic before consequential planning.

## Tags and structured fields

Tags/hashtags are retrieval aids. They do not replace structured semantics.

Prefer `type`, `status`, `goal-alignment`, provenance, relationships, and freshness fields for meaning. Tags may duplicate important concepts to improve simple text search and portability across stores that lack structured indexing.

## Content and metadata separation

Human-readable content may remain in a clean canonical document while searchable/indexable metadata lives in a sidecar or structured index.

An adapter may also store both together when appropriate. Consumers must not depend on a particular folder layout or sidecar mechanism.

The metadata layer should link back to the canonical object and preserve stable IDs so a later database migration does not require rewriting relationships.

## Capture rule

When an authorized agent is asked to remember something durably:

1. classify the record;
2. preserve the smallest durable meaning rather than the whole conversation;
3. connect it to existing goals/relationships when explicitly supported;
4. record provenance;
5. mark stale-prone fields as dynamic;
6. add retrieval metadata;
7. write through the configured permanent-memory binding;
8. avoid creating new physical storage structure unless the adapter/memory method requires it.

Dated operational observations belong in evidence/event storage unless they have been deliberately promoted to durable knowledge.

## Adapter boundary

Storage adapters own:

- physical paths/folders/tables;
- provider IDs;
- serialization details;
- transport/authentication;
- provider-specific indexing.

The portable memory layer owns:

- semantic record type;
- stable ID;
- goal/relationship links;
- provenance;
- freshness meaning;
- lifecycle/status;
- retrieval hints.

This boundary permits migration from the current file/Drive bootstrap to another memory backend while preserving meaning.
