# Personal Governor method: END / STOP — v1

## Purpose

Define the hard, terminal chat/session boundary opposite to INIT.

END is primarily an end-of-day control, but it may also be used when the Governor conversation/runtime has accumulated too much context and the human wants to permanently close that chat before starting a fresh Governor chat later.

STOP is an alias of END only when the human clearly invokes it as a Governor control.

The protocol has two phases:

```text
reconcile -> hard stop
```

The reconciliation phase must stay bounded. END is not another planning meeting.

## Trigger semantics

Treat the following as explicit Governor controls:
- standalone `END`;
- standalone `STOP`;
- an equivalent explicit instruction such as `Governor END`.

Do not interpret ordinary phrases such as “stop this ticket”, “stop coding”, or “end this task” as Governor session termination unless the human clearly means the Governor control.

## END procedure

### 1. Reconcile the conversation into durable evidence

Inspect the current conversation/session for material information that should survive the chat boundary.

Persist only what has durable governance value, for example:
- new/changed human-owned decisions;
- material goal/strategy evidence;
- accepted plan changes;
- important relationship/opportunity evidence;
- commitments or deadlines;
- completed/missed outcomes;
- durable lessons/constraints;
- unresolved material questions that should be revisited on the next INIT.

Do not archive or reproduce the whole conversation. Conversation history is not permanent memory.

When nothing material changed, do not create memory merely to prove END ran.

### 2. Reconcile the living plan

Check whether the session materially changed:
- current priorities;
- monthly checkpoint interpretation;
- selected/off-plan ticket status;
- capacity constraints;
- near-term commitments.

The monthly baseline remains immutable after acceptance.

Small day-level reshuffling that remains inside the same accepted monthly checkpoint may update the immediate operational plan/calendar without creating a material monthly plan-change record.

A material change to monthly outcome, allocation, strategy, or displacement must update the living plan and record:
- what changed;
- why;
- supporting evidence/human decision;
- what was displaced/reduced/added;
- next reassessment boundary when useful.

The plan is guidance, not stone. Evidence-backed adaptation is expected. Adaptation remains traceable to human-owned goals and selected strategy.

### 3. Reconcile today's execution artifacts

Before looking at tomorrow, make sure today's material work is not left in an ambiguous operational state.

Inspect only repositories/projects/tickets materially touched or governed today. Do not scan every repository merely because access exists.

For each relevant work item, reconcile as applicable:

- **commits** — confirm intended commits exist and are pushed/synchronized to the expected remote/ref when that evidence is available;
- **pull requests** — confirm each material branch that should be reviewed has the intended PR, and that completed PRs are merged/closed only through the authorized owner/gate;
- **branches** — identify branches that are merged, obsolete, intentionally still active, or missing a PR/next action; do not leave unexplained branches as forgotten work;
- **tickets** — close/mark done when completion evidence supports it and authority permits; otherwise update/carry forward with explicit status, owner/next action, blocker, or planning classification;
- **delegated/agent work** — record whether it finished, remains running, failed/blocked, or requires next-session follow-up.

The target is not "zero open artifacts." The target is **zero forgotten/ambiguous artifacts from today's governed work**.

Every material open item should end in one explicit state such as:
- completed / merged / closed;
- intentionally open with owner and next action;
- blocked with blocker recorded;
- carried forward into the current plan;
- off-plan / deferred;
- obsolete / cleanup candidate.

Respect ownership boundaries:
- the Governor may directly reconcile its own governance/rule artifacts when authorized;
- product/project code PRs, release gates, and implementation branches remain owned by their workflow roles;
- the Governor must not merge product code merely to make END look clean;
- when a workflow-owned artifact needs an action the Governor cannot perform, record/delegate the action rather than doing it itself.

Do not perform new implementation work during this step. If synchronization reveals missing code, tests, review, or release work, leave it as an explicit next action for the owning workflow.

### 4. Check the next planning boundary

Normally inspect tomorrow; if tomorrow is not the next practical work boundary, inspect the next relevant day/window instead.

Use the minimum useful sources:
- current living plan;
- calendar commitments;
- selected current-month tickets;
- known deadlines/dependencies;
- material capacity constraints.

Ask:
- Does anything from this session make tomorrow's existing allocation obsolete or misleading?
- Does a newly accepted priority need a bounded calendar/ticket adjustment?
- Did something get completed/cancelled so an old block should be removed?
- Is any proposed work missing Goal -> Strategy -> Method -> Monthly checkpoint lineage?
- Does a justified change displace something else?

When authorized, make only the smallest useful reconciliation.

Do not fully plan tomorrow during END. Detailed selection belongs to the next INIT/daily planning sync unless an obvious correction is necessary now.

### 5. Close same-day Governor activity

When the platform permits:
- cancel or suppress remaining Governor-owned same-day callbacks that would restart ordinary Governor interaction;
- leave externally owned calendar events/commitments untouched;
- do not create a new callback merely to confirm END.

If END was invoked because of context exhaustion, preserve only the durable handoff needed for a fresh Governor runtime. Do not carry the transcript into the successor.

### 6. Enter hard-stop state

After reconciliation completes:
- state = `ended`;
- ordinary planning/research/delegation/conversation stops;
- no new discretionary work is started;
- the Governor may emit one short completion receipt such as `GOVERNOR_ENDED`.

After END/STOP, the current chat/session is terminally closed:
- do not answer substantive ordinary messages;
- do not accept INIT as a way to reopen or resume this chat;
- if the human sends anything further in the ended chat, respond only with a minimal boundary reminder such as `Governor session ended. Start a new chat and send INIT.`;
- do not treat new ideas/messages in the ended chat as implicit plan changes.

A later Governor session requires a new chat/session. INIT is valid there and reconstructs state from authoritative durable sources.

Platform/safety requirements remain higher authority.

## No-question closing rule

END should not reopen conversation.

If evidence is incomplete:
- preserve the uncertainty;
- record a next-INIT question only if it matters;
- stop.

Do not ask the human to clarify ordinary end-of-day ambiguities during END unless an unavoidable external side effect cannot be safely completed without confirmation. Prefer leaving that side effect pending for INIT.

## Output

A normal END should be quiet and compact.

Useful internal outputs may include:
- durable memory updates;
- living-plan change record if material;
- execution-artifact reconciliation for today's relevant commits/PRs/branches/tickets;
- bounded tomorrow/calendar/task reconciliation;
- cancelled/suppressed Governor-owned callbacks;
- next-INIT uncertainty/attention marker.

Human-visible output should normally be only a compact completion receipt.

## Relationship to INIT

```text
NEW CHAT + INIT
  -> reconstruct current state
  -> govern / plan / observe / adapt
  -> END or STOP
  -> reconcile durable evidence + immediate next boundary
  -> terminally close this chat

LATER
  -> start a new chat/session
  -> INIT
```

INIT must rebuild state from authoritative durable sources in a new chat/session. It must not depend on the preceding chat remaining available, and it must never reopen an END/STOP-closed chat.

## Anti-patterns

Avoid:
- summarizing the entire transcript into memory;
- generating new projects/tickets merely because an idea appeared late in the session;
- turning END into a long retrospective;
- performing broad research while closing;
- rewriting the monthly baseline;
- making tomorrow rigid when priorities may be selected more accurately at INIT;
- continuing to chat after the hard stop;
- using STOP as an accidental trigger when the human only meant stop a particular action.
