# Research Before Build — v1

Use this method when a proposed capability, architecture, infrastructure component, or substantial implementation could consume meaningful engineering attention.

## Purpose

Reduce avoidable reinvention. Treat model-generated designs as hypotheses and starting vocabulary, not sufficient evidence that a proposed architecture is necessary, established, or appropriate.

## Method

1. **Define the problem and requirements first.** Record the outcome, constraints, non-goals, portability/ownership needs, acceptable operating cost, and what would count as success. Do not select a technology before the problem is clear.
2. **Search for real implementations.** Look for established products/services, maintained open-source projects, comparable architectures, repositories, issue trackers, benchmarks, operational reports, and credible user experience. Prefer inspectable implementations over marketing claims.
3. **Inspect evidence, not names.** Establish what the system actually does, why relevant choices were made when evidence exists, maturity/maintenance, failure modes, operational burden, licensing, and important limitations. Separate documented fact from inference or anecdote.
4. **Compare against the requirements.** Identify which requirements are already solved, which remain gaps, and whether adopting an existing solution would create unacceptable dependency, cost, control, privacy, portability, or differentiation trade-offs.
5. **Choose explicitly:** **adopt / integrate / borrow pattern / deliberately differ / build**.
6. **Bound experiments.** If evidence is insufficient, run the smallest comparison or proof of concept that can resolve the important uncertainty. Do not begin a large implementation merely to learn whether the premise was correct.
7. **Record the rationale.** Preserve the alternatives, evidence, decision, rejected trade-offs, and trigger for reconsideration.

## Evidence hierarchy

For implementation/architecture questions, prefer evidence in roughly this order when applicable:

- running or inspectable implementations and source code;
- official technical documentation and design material;
- issue/PR history, benchmarks, operational reports, and reproducible tests;
- credible practitioner/user experience;
- secondary analysis;
- model-generated suggestions without external verification.

The order is guidance, not an automatic truth ranking. Evaluate relevance, recency, incentives, reproducibility, and whether the evidence matches the actual requirements.

## Governor behavior

The Governor should invoke or recommend this method before allocating substantial attention to building a capability that may already exist. It should not turn every small implementation choice into a research project. Research depth must be proportional to expected engineering cost, irreversibility, strategic importance, and uncertainty.

Existing solutions are evidence, not authority. A mature project may solve a different problem. Deliberately building something new is valid when requirements, differentiation, control, ownership, learning value, or constraints justify it.

## Output

A compact decision record:

- problem / requirements;
- comparable systems examined;
- material evidence and limitations;
- build-vs-existing trade-offs including human attention/operations cost;
- decision: adopt / integrate / borrow pattern / deliberately differ / build;
- smallest next action;
- reconsideration trigger.
