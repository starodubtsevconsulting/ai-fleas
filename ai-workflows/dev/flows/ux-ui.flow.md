# UX and UI flow

## Purpose

Apply this linked [Dev workflow](../dev.workflow.md) flow when an assignment changes a user-visible page, component, navigation path, form, or responsive layout. It supplies design and verification checkpoints within the existing planning, implementation, testing, review, and UI acceptance stages. It does not create a new role or replace independent UI acceptance.

## Entry

Identify the authorized project, affected routes and states, intended user task, existing design system, current rendered behavior, and delivery scope. Identify every language the affected page or app supports and how a user switches between them. Inspect the actual interface before assuming what is on screen. Use the [UX review template](../guides/ux-ui-review-template.md) to record the chosen checks and evidence. Include only applicable checks; explain exclusions that could affect acceptance.

## Steps

1. **Designer / Reviewer, during planning:** Walk the current user path and inspect the affected screen at a representative narrow phone width and desktop width. Include an intermediate width when a layout changes there. Record the baseline, the desired action and content hierarchy, and acceptance criteria for navigation, content, responsive behavior, and relevant empty, loading, error, and success states. For a localized surface, list every supported language and include language-specific text length, navigation, and state changes in the acceptance criteria. Use existing components and visual patterns where they serve the task.
2. **Coder, during implementation:** Make the bounded change. If the affected page or app supports localization, update every supported language for any changed visible text or behavior, including controls, help text, accessibility labels, validation and status messages, and relevant metadata. Reuse the existing localization mechanism and keep language-specific routes and links coherent. Do not let an untranslated fallback silently stand in for a completed language. Keep content legible and controls usable as available width changes; let content scroll where it cannot fit. Preserve keyboard access, visible focus, meaningful labels, and the intended interaction. Recheck the rendered page as work progresses, using the project's development mode when it gives reliable feedback. A production build is required only by an applicable project or delivery gate.
3. **Designer / Reviewer, during verification:** Inspect the current candidate at the chosen viewports and exercise the affected user path in every supported language. Check the language switch, translated text and accessible names, clipping and horizontal overflow, text wrapping, spacing, scroll reachability, touch and keyboard controls, links or form behavior, and relevant states. Compare observations with the baseline and acceptance criteria. Save dated screenshots or a short recording when visual evidence helps review; identify route, language, viewport, candidate revision, and environment. A screenshot alone does not prove interaction behavior.
4. **Command Runner:** Run the focused registered checks selected by the parent [testing flow](testing.flow.md). **Designer / Reviewer** records their results separately from visual inspection. Failed behavior enters the parent [debugging flow](debugging.flow.md), followed by the affected checks again.
5. **Designer / Reviewer and UI Acceptance Tester:** Review the implementation and coordinate independent visible acceptance at the parent UI checkpoint. Record what passed, failed, or was not run, including the reason and next owner for an unresolved item. The person who implemented the change cannot self-certify independent UI acceptance by relabeling their own inspection.

## Exit

Return to the next parent Dev checkpoint with a candidate-bound [UX review record](../guides/ux-ui-review-template.md), focused check results, and any required independent UI receipt. A localized surface is incomplete if a supported language lacks the changed content or the affected user path has not been checked in that language; record an explicit blocker rather than accepting a silent fallback. Keep deployment and production verification in the parent workflow; local rendering does not establish production behavior. When a change affects only copy or one component, keep the review proportional to that surface and its adjacent path.
