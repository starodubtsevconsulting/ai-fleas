# macOS distribution flow

## Purpose and applicability

[Dev](../dev.workflow.md), planning through delivery/deployment and closure, whenever a product includes a macOS binary or changes its packaging, signing, entitlements, distribution channel, update behavior or purchased delivery. This flow refines existing Router stages and role ownership; it adds no role, runtime state or permission. Product documents apply this canonical flow to their release and evidence instead of owning a competing checklist.

## Entry

Manager resolves the authorized product/repository, staffing, tracker and recovery point. Designer / Reviewer records the technical plan, baseline/intended candidate, selected phase/channel, already authorized effects and required evidence. Bind exact artifact/hash identity when the candidate becomes available. Determine whether website distribution, Mac App Store distribution, or both apply. Resolve missing human commercial/signing authority before dependent effects; reuse existing authorization without asking again. A plan, source build or checklist is not a release receipt.

## Steps

1. **Manager: work target.** Resolve scope, staffing and tracker coordination. **Designer / Reviewer: technical plan and criteria.** Define independently reviewable implementation/verification slices, owners and required evidence. Separate Developer ID signed/notarized website distribution from a distinct sandboxed Mac App Store build and Apple review/store hosting. Define supported OS/architectures, actual functionality, update/rollback behavior and clean installation tests. Follow [planning](planning.flow.md).
2. **Human authority, when required by the selected phase/channel.** The human/account holder supplies actual legal identity and enrollment, applicable agreements, banking/tax information, signing authority and release/commercial decisions. Agents may prepare reviewable material and execute already authorized supported actions; they never fabricate account answers, bypass identity checks or perform human-only financial gates. Missing facts block only the dependent step.
3. **Coder: implementation.** Implement scoped packaging/signing configuration, bundle ID/version/build, provisioning and app/helper entitlements, dependency/license/privacy requirements and update behavior. For the selected Mac App Store route, Electron uses the appropriate MAS build and must prove Apple App Sandbox feasibility independently of renderer sandboxing. Child-process utilities and power assertions must work under that App Sandbox; website/preview phases use their selected functional tests without requiring a MAS build. If the store sandbox does not support the behavior, propose an allowed public API/helper design rather than bypassing security. No approval guarantee follows from a successful build.
4. **Command Runner: applicable mechanical proof.** Through configured commands, build the exact candidate, package and verify signatures/entitlements. For an authorized signed website release perform Developer ID signing/notarization and verify results; for an authorized store release validate the separate store archive and perform authorized upload. Record actual terminal outcomes and artifact identity; a queued upload or dispatch is not notarization/review approval. Follow [testing](testing.flow.md) and [delivery guidance](../guides/delivery.md).
5. **Designer / Reviewer: independent review.** Review source, dependencies, permissions, manifests, distribution claims and channel-specific acceptance evidence. Verify truthful privacy/export declarations and screenshots/support/review notes against observed behavior. Store review feedback returns to existing debugging/implementation stages; agents cannot self-certify Apple acceptance.
6. **UI Acceptance Tester: visible proof.** Test the packaged preview, clean quarantined website installation or genuine store installation required by the selected phase/channel on supported targets. Verify launch, primary controls, permissions, child/process cleanup, update and uninstall behavior; distinguish manual source-runtime smoke from packaged installation. Record unrun targets and limitations explicitly.
7. **Command Runner and Designer / Reviewer: authorized release and handoff, when applicable.** Publish only the authorized verified artifact/channel through [deployment](deployment.flow.md). Keep an immutable manifest with product/version/build, source commit, toolchain/dependencies, build time, OS/architecture, license review, signing/notarization/review state, SHA256/bytes and smoke evidence. Keep binaries private where required; retain purchased versions, verify off-device backup restoration and rollback access. Hand commerce the exact immutable artifact and observed evidence; commerce owns pricing, authenticated entitlements, customer receipts and refund/revocation behavior. Store and website purchase/refund channels are distinct unless explicitly implemented and verified.
8. **Manager: closure.** Record the completed phase and exact candidate/channel, terminal results, applicable independent review/installation proof, human decisions and remaining limitations; identify an actual release only when its evidence exists. Missing signing, review, restore or installation proof required by the selected release plan remains an open gate; do not report release completion from source or checklist alone.

## Exit and recovery

Return evidence to the existing verification, independent review, UI acceptance, delivery/deployment and closure stages. The selected bounded phase is complete when its required evidence exists. Source/package development and explicitly authorized unsigned preview/testing may complete without Apple enrollment, signing, store approval or backup restoration when those effects are outside the selected plan. Record unrun production channel gates as open; preview completion never establishes production/store readiness. Require release and installation proof only for the selected release phase/channel, not an unselected alternative channel. Preserve failed candidate/channel evidence, diagnose through [debugging](debugging.flow.md), and reassess the new immutable candidate. Do not overwrite prior purchased bytes or infer account access, credential changes, publication or financial authority.

## Official references

References checked 2026-10-11; recheck current requirements before an actual release:

- [Apple macOS distribution](https://developer.apple.com/macos/distribution/), [distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/) and [notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution/) define the website/store routes.
- [Developer enrollment](https://developer.apple.com/programs/enroll/), [agreements](https://developer.apple.com/help/app-store-connect/manage-agreements/sign-and-update-agreements/) and [tax information](https://developer.apple.com/help/app-store-connect/manage-tax-information/provide-tax-information/) support human account/commercial preparation.
- [App Privacy](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy/), [export compliance](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance/) and [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) support truthful submission criteria.
- [Electron MAS submission](https://www.electronjs.org/docs/latest/tutorial/mac-app-store-submission-guide) describes the distinct build, signing and sandbox constraints; it does not establish compatibility for a particular product.
