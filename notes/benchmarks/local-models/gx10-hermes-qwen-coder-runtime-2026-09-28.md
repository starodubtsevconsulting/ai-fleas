# GX10 Hermes Qwen Coder runtime trial — 2026-09-28

This trial asked whether Hermes compression and CLI controls improve **independently accepted coding work per minute** for Qwen3-Coder-Next Q5_K_M. It used the frozen [financial recognizer coding fixture](fixtures/hermes-financial-recognizer-coding/README.md), a 65,536-token served context, Hermes v0.21.0, and fresh sessions. The model server was unchanged. The independent verifier includes positive French and English cases, missing-signal rejections, whole-word `PAYMENT` negatives, and evidence flags.

## Compression comparison

The old settings were `threshold=0.25`, no absolute token threshold, `target_ratio=0.15`, and `protect_last_n=8`. The proposed settings were `threshold=0.75`, `threshold_tokens=32768`, `target_ratio=0.20`, and `protect_last_n=20`.

| Settings | Run 1 | Run 2 | Accepted results | Compaction |
|---|---:|---:|---:|---|
| Old | 64.78 s, 4 calls, fail | 26.90 s, 4 calls, pass | 1/2 | None |
| Proposed | 64.12 s, 6 calls, pass | 31.34 s, 4 calls, pass | 2/2 | None |

The wall-time ranges overlap. The largest single-call input was 11,884 tokens, below the proposed 32,768-token trigger. These **coding runs** cannot establish a compression speed or quality effect. A separate concise-prompt pair took 25.15 and 26.64 seconds but passed only one of two runs. Adding an explicit whole-word boundary example also passed only one of two after the verifier added a coexistence case. Neither prompt variant is an accepted default.

A separate **read-only, five-turn code-review probe** crossed the cap with frozen public Hermes runtime source packets. Under old compression settings it finished in 89.52 seconds without compaction. With the proposed 32,768-token cap and 20 protected messages, turn five spent 53.20 seconds compressing but shrank only from about 50,967 to 47,703 estimated tokens; it immediately began another summary and hit a 120-second outer limit without a final answer. Reducing the protected-message count to 3 produced the same repeated-compression outcome. A 49,152-token cap completed after one 47.69-second summary, but the five turns took 151.70 seconds and the final answer missed the specific review question. Single runs and prompt-cache order limit broad speed claims, and this is not a coding acceptance test. They do show that the proposed early cap can add substantial latency without clearing its own threshold in a real multi-turn source review. Keep the existing realized compression settings pending an accepted-code comparison.

The successful long-patch call generated 1,828 output tokens and took 35.2 seconds. A 1,024- or 1,536-token output cap risks truncating that useful tool call; a 2,048-token cap would not shorten it. Model generation and the number of turns dominated these short runs, while file tools took roughly 1–1.5 seconds per run.

## Task-specific handoff improvement

The recognizer's repeated false positive had a concrete cause: Coder implementations often checked `PAYMENT` as a whole word in `normalizedText` but also used `compactText.includes('payment')`, which accepts `REPAYMENT`. A frozen prompt addition stated that `normalizedText` preserves word boundaries, `compactText` may concatenate words and must not be substring-searched for English `PAYMENT`, and standalone `PAYMENT` still counts beside `REPAYMENT`. It also requested direct file-tool work and a one-sentence completion. The original task and verifier were unchanged; all runs used the same Q5 profile, CLI route, exact-file write boundary, frozen starter, and 180-second outer limit. Eight baseline and eight clarified runs were interleaved, each in a fresh session, with the starter restored between runs.

| Handoff | Accepted / runs | Total Coder wall time | Mean per run | Accepted results per minute | Model calls | Output tokens |
|---|---:|---:|---:|---:|---:|---:|
| Frozen baseline | 2/8 | 319.42 s | 39.93 s | 0.376 | 40 | 12,690 |
| Boundary-source clarification | 8/8 | 243.49 s | 30.44 s | 1.971 | 35 | 9,175 |

The independent verifier covered French preservation, English positive and negative cases, the `PAYMENT`/`REPAYMENT` coexistence case, evidence flags, and the result contract. All processes exited, no arm compacted, and the checkout target was restored after every run. The clarified prompt produced about **5.2 times as many accepted results per Coder minute on this fixture**. An intermediate two-run prompt that mentioned whole words without distinguishing `normalizedText` from `compactText` passed only 1/2, reinforcing the source-representation explanation. The [sanitized per-run record](gx10-word-boundary-pilot-2026-09-28.json) is checked in; raw local outputs and session IDs are in ignored `runs/sc-word-boundary-pilot-2026-09-28/`. This is a narrow text-recognition task, not evidence that Hermes compression or general multi-step coding improved; cache order and only eight runs per matched arm limit broader speed claims. For similar recognizers, specify which representation preserves the invariant and verify both false positives and coexistence.

## Larger coding and loop behavior

Two synthetic publication implementations, each with one correction, failed an existing ownership and collision behavior test. A smaller historical amount-recognizer repair started at 4/5 passing cases; its first edit and correction each passed only 1/5. These trials produced **no accepted larger implementation**, so faster completion text is not a usefulness gain.

A later one-file process-group helper task gave a more precise result. An independent PID diagnostic proved that the frozen starter left descendants alive after timeout. The local Coder spent about 55 seconds on its first staged fix and about 41 seconds on one correction. The corrected file passed timeout checks for ordinary and SIGTERM-resistant descendants, but an external-SIGTERM check still left the resistant descendant running. The diagnostic cleaned up its captured group, and the production helper was untouched. This is **partial behavior after about 96 seconds, not accepted code**; it reinforces the need to include signal and descendant cleanup in the verifier before comparing runtime settings.

The [process-group fixture](fixtures/hermes-process-group-timeout/README.md) now has an independent, file-free verifier. It fails the frozen starter's timeout and signal paths, distinguishes the partial timeout fix, and passes a reviewed reference candidate. In a later four-run fresh-start pilot, two baseline and two explicitly clarified handoffs all failed its timeout, SIGTERM, and SIGINT descendant checks. One clarified run hit the 180-second outer limit; a baseline made 20 model calls and exited normally with incorrect code. All four implementations conditioned group SIGKILL on the direct child's wait timing out and left signal-resistant descendants alive. The [sanitized per-run record](gx10-process-group-prompt-pilot-2026-09-28.json) reports the timings and case results. The recognizer's prompt improvement **did not transfer** to this harder lifecycle task; 0/4 accepted results cannot support a speed gain, regardless of completion time.

A follow-up gave the Coder the exact cleanup sequence: signal the process group, wait at most five seconds for the direct child, unconditionally send SIGKILL to the group even if that child exited, then reap the child. Two fresh implementations still placed SIGKILL inside the direct-child timeout branch and failed all three tree cases (52.63 and 28.55 seconds). Each got one verifier-backed correction. The first correction passed six cases but had an early `ProcessLookupError` return before reaping, so review rejected it. The second correction passed all six cases and source review in another 24.09 seconds, for **52.64 seconds of Coder time to one accepted staged helper**. The [sanitized record](gx10-process-group-algorithm-2026-09-28.json) separates verifier pass from source-review acceptance. This is evidence that a precise algorithm plus correction can produce useful code here; it is not a parameter speedup or a matched comparison with the earlier prompt pilot.

The accepted staged helper was then assigned for a one-file production port through the configured Coder route. The run took 143.92 seconds, ended with `max_iterations_reached(20/20)`, and made 17 successful patch calls, many after the target already matched the requested source. One wrong-path patch was denied by the exact-file write boundary. Despite its incomplete final turn, the authorized production file was byte-identical to the accepted staged helper. Independent source review, all six process-group verifier cases, `git diff --check`, and installer shell syntax passed. This fixes the repository helper on this branch, but the 144-second port and repeated no-change patching show that the bounded runtime still wastes substantial time. The currently installed Hermes runtime and compression settings were not changed.

A subsequent turn-cap pilot asked for that same source-to-target port from the same frozen starter four times, with the same accepted reference, model, route, write boundary, verifier, and 180-second outer limit. The sole treatment was the live profile's `agent.max_turns`, changed for each run and byte-restored afterward. Runs alternated 6, 20, 20, 6 turns. All four outputs matched the reference and passed the six-case verifier. The 6-turn runs took 59.91 and 65.96 seconds and both reached the cap, triggering a summary request. The 20-turn runs took 34.85 and 58.85 seconds, finishing normally after 4 and 7 model calls. Mean accepted wall time was 62.94 seconds at six turns versus 46.85 at twenty, so **lowering the cap to six did not improve accepted work per minute on this port**. The [sanitized per-run record](gx10-turn-cap-pilot-2026-09-28.json) includes calls and tool counts. Two runs per arm, variable model paths, and a source-copy port rather than independent problem solving limit generalization. The original 20-turn live setting remains in place.

One historical Hermes turn logged 313 model calls and more than 300 repeated file writes. A later bounded launcher edit still spent five patch calls on a file that already contained the requested change; four consecutive calls used identical patch arguments. The installed guard did not stop that no-change loop. Hermes [v2026.9.7 added an identical-call halt](https://github.com/NousResearch/hermes-agent/blob/v2026.9.7/agent/tool_guardrails.py), but it has not been tested live on this deployment. A historical trace replay suggests it targets a real failure mode; it does not prove accepted code or a measured speedup.

The accepted production port provides a more discriminating guard replay. Its exported session had 20 model calls and 18 patch requests; **16 patch requests had identical `old_string` and `new_string` arguments**. The model varied the selected text between requests, so there was no pair of consecutive identical patch arguments. The longest repeated exact-call cycle was a three-call pattern for two laps. The v2026.9.7 consecutive-call guard would not have stopped that run; the [v2026.9.14 cycle guard](https://github.com/NousResearch/hermes-agent/blob/v2026.9.14/agent/tool_guardrails.py) also requires more repeated laps than occurred here. The [sanitized replay](gx10-guard-replay-2026-09-28.json) records these counts without session contents. This is a trace-based applicability check, not live behavior of either newer release. The [v2026.9.7 release](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.9.7) rolls up thousands of commits since the pinned v0.21.0 runtime, so replacing the shared install solely to test this guard would change many variables at once.

## CLI route control

The old launcher used top-level `hermes -z`. That path ignores configured `agent.max_turns`, as confirmed by a stopped 28-call run and by [upstream issue #105243](https://github.com/NousResearch/hermes-agent/issues/105243). Its 240-second run budget asks the model to wrap up but is not a process deadline. The issue remains in the [v2026.9.14 one-shot source](https://github.com/NousResearch/hermes-agent/blob/v2026.9.14/hermes_cli/oneshot.py).

The configured launcher now uses `hermes chat -Q --query`, which keeps answer-only stdout while applying the profile's 20-turn limit. A live smoke run logged `api_calls=1/20`. CLI `run` rejects a missing `HERMES_WRITE_SAFE_ROOT`; the caller must supply the exact authorized file or directory. Shell syntax, route readiness, missing-guard rejection, and a write-denied smoke run passed. A turn-limit summary can exit successfully despite incomplete work, so the caller must independently verify output.

The CLI route now wraps the same Hermes command in the independently verified process-group deadline helper. Its default is 240 seconds until cleanup begins, with up to five seconds for graceful exit; `HERMES_CODER_TIMEOUT_SECONDS` can set a positive integer for one run. The first Coder implementation took 163.00 seconds, reached 20 model calls, and repeatedly wrote an unrequested empty file; Admin removed that file after process exit. Review found that an explicitly empty override silently selected the default. One focused correction took 43.82 seconds and fixed that behavior. The correction itself completed through the new wrapper with the real local Coder. An independent fake-command integration probe then passed nine checks: `check` remained independent of the timeout variable, missing write scope and empty/noninteger/nonpositive overrides failed before launch, normal exit status and the unset default worked, and a one-second timeout killed a SIGTERM-resistant descendant, emitted a generic diagnostic, and exited 124. The helper's six process-group cases still pass. The [sanitized verification record](gx10-cli-deadline-verification-2026-09-28.json) is checked in. This bounds runaway CLI runs; it is not a measured improvement in accepted coding speed and does not validate A2A cancellation.

With the bounded route, the frozen recognizer took 42.96 seconds and 6 model calls on its first attempt, which failed the `REPAYMENT` negative. One correction took 40.94 seconds and 9 calls; the saved result passed the full verifier. That is **one accepted small change after 83.90 seconds and 15 calls**. The changed handoff and correction prevent a direct speed ranking against the four compression runs. The controlled result establishes that the bounded route can produce accepted work with review; it does not show a faster or generally more capable agent.

## Decision

Keep the existing Q5 model, compression settings, and 20-turn cap. CLI controls now enforce write scope selection and a hard process deadline; the task-specific boundary-source wording improved accepted work per minute on the frozen recognizer. The algorithmic handoff produced one accepted process-group fix after correction, while its production port reproduced costly repeated patching. Lowering the cap to six increased time on a matched source-port pilot. These results have not established a general coding or Hermes-parameter speedup. A newer identical-call halt remains a candidate for the historical identical-write streak, but does not match the accepted port's varied no-op patches. Next, run a long coding fixture that actually crosses the compression trigger, then test any guard upgrade in an isolated, reviewed runtime comparison. Compare pass rate, total wall time, model calls, tool repetition, scope errors, and post-compaction correctness with the same start and independent verifier.
