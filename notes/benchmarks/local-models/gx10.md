# ASUS Ascent GX10 — local coding-worker models

Benchmarked on a single ASUS Ascent GX10 with NVIDIA GB10 and 128 GB unified memory. The earlier Qwen and Gemma models were served with `llama.cpp`/CUDA; DeepSeek V4 Flash was served with `ds4`/CUDA. Those candidates were exercised through Hermes Agent using the same local OpenAI-compatible endpoint and controlled tool-use fixture. The later Qwen3.6 35B NVFP4 dual-loaded test used vLLM and could not enter the Hermes fixture at its configured context.

## Purpose

Evaluate the GX10 as a heavyweight local worker for substantial coding/agent tasks where model capacity, long context, reliable tool use, and useful sustained throughput matter more than minimum interactive latency. The practical winner must pass the same Hermes workflow while retaining safe unified-memory headroom.

## Takeaways

The GX10 is a **good fit for heavyweight local worker agents** where model capacity matters more than maximum interactive speed.

### Pros

- **128 GB unified memory is the main advantage.** It can run models far beyond the practical VRAM ceiling of the RTX 3080 Ti workstation.
- **Large models remain genuinely usable.** Qwen3-Coder-Next Q5_K_M generated 55.68 tok/s and completed the Hermes tool-use task in 21.94 seconds.
- **Hermes tool use works for the preferred candidates.** Both Qwen models and DeepSeek passed the same practical file/tool workflow and independent output verification; Gemma completed the transformation but failed output-location compliance.
- **Compact worker-box form factor.** It is much better suited than a full-size workstation to building a modular local AI cluster.
- **Good scaling direction.** Additional GX10-class boxes can be added as independent workers or, where supported, combined for larger distributed inference.

### Cons

- **Large-model capacity does not guarantee better practical throughput.** Qwen3.5-122B-A10B fits comfortably but generated only 22.16 tok/s and took 149.23 seconds for the tested Hermes task.
- **The larger tested model had a much slower cold load:** 66.14 seconds versus 7.29 seconds for Qwen3-Coder-Next.
- **DeepSeek V4 Flash is unsuitable for our single-GX10 coding worker.** The compressed build peaked at 109.91 GiB total unified-memory use and generated only 16.32 tok/s at 2K context, falling to 12.94 tok/s at 65K. Its Hermes fixture took 133.85 seconds versus 21.94 seconds for Qwen3-Coder-Next Q5_K_M. Passing the fixture establishes compatibility, but does not justify this speed and memory cost for our use case.
- **Gemma 4 31B Q8_0 is slow and failed the controlled tool-use acceptance.** It generated 6.80 tok/s and wrote correct fixture contents to the wrong directory, so it is an opt-in chat/quality experiment rather than an accepted worker.
- **Qwen3.6 35B NVFP4 is blocked as a Hermes worker in its dual-loaded configuration.** Its short direct API runs were fast, but the served 32,768-token context is below Hermes Agent's 64,000-token minimum. A longer sequential request also caused swap-out with both models loaded.
- **The Gemma variant deliberately removes refusal behavior.** Its Apache-2.0 weights remain separately selectable, but the operational mode must be treated as an explicit uncensored experiment rather than a safety-controlled default.
- **Price is significant**, especially when the intended architecture grows by adding multiple boxes.
- **It is not automatically the best machine for every agent.** Small latency-sensitive agents can be served more efficiently by faster fully GPU-resident models on existing conventional GPUs.

The practical role is therefore **large local worker capacity**: use GX10-class machines for substantial worker agents and models that need large memory, while smaller hardware such as the RTX 3080 Ti workstation can handle fast System-agent and micro-command workloads. The current single-GX10 default is **Qwen3-Coder-Next Q5_K_M** because it provides the best balance measured so far between model capability, speed, and successful Hermes tool use.

## Hermes tool-use baseline

The reproducible baseline required the agent to read a file, sort and deduplicate its contents, write two output files, count lines, calculate SHA-256, and verify the outputs. Results were independently checked after the agent completed the task.

The exact task, input, expected outputs, and independent verifier are preserved in the [Hermes file-tools fixture](fixtures/hermes-file-tools/README.md).

For Qwen3-Coder-Next the run used 6,382 input tokens and 620 output tokens and passed independent verification. DeepSeek V4 Flash also passed independent verification. Its `ds4` adapter reported 795 output tokens, 63,613 cache-read tokens, and 21,142 cache-write tokens across four API calls; it reported prompt work through cache accounting rather than the ordinary input-token field.

Gemma used 13,604 input tokens, 1,111 output tokens, 38,319 cache-read tokens, and four API calls in 249.60 seconds. It produced byte-correct normalized and report contents but placed them in the fixture source directory rather than the requested isolated run directory. The independent verifier therefore failed, and the misplaced outputs were preserved outside the repository as private diagnostic evidence.

## DeepSeek V4 Flash context and resource sweep

The direct DeepSeek run used the pinned [`ds4`](https://github.com/antirez/ds4) CUDA runtime and the exact 80.76 GiB [community GGUF artifact](https://huggingface.co/tekosML/DeepSeek-V4-Flash-0731-GGUF-GX10). The artifact checksum was verified before loading. The context sweep generated 128 tokens at every point:

|---:|---:|---:|---:|---:|
| 2,048 | 2,048 | 387.10 tok/s | 16.32 tok/s | 16.45 tok/s |
| 4,096 | 2,048 | 383.93 tok/s | 14.40 tok/s | 14.46 tok/s |
| 8,192 | 4,096 | 381.12 tok/s | 14.13 tok/s | 14.20 tok/s |
| 16,384 | 8,192 | 370.14 tok/s | 14.05 tok/s | 14.13 tok/s |

| 65,536 | 32,768 | 307.97 tok/s | 12.94 tok/s | 13.00 tok/s |

During the sweep, total used unified memory peaked at **109.91 GiB**, active-test memory increased by **106.70 GiB**, sampled GPU utilization peaked at **96%**, and mean non-zero GPU utilization was **88.85%**. The machine retained approximately 11.7 GiB of available memory at the worst sampled point. This is adequate for a dedicated worker but leaves much less operational headroom than Qwen3-Coder-Next.

The direct Qwen and DeepSeek throughput figures use their respective native benchmark tools and therefore compare deployed runtime outcomes rather than identical inference engines. The controlled Hermes fixture is the cross-runtime acceptance test.

## Gemma 4 31B IT Uncensored Q8_0 context and resource sweep

The Gemma run used the exact 32,635,670,112-byte [TrevorJS Q8_0 GGUF artifact](https://huggingface.co/TrevorJS/gemma-4-31B-it-uncensored-GGUF) with SHA-256 `682fdd418adb31386dc7809d4966ec88e33bd1b9bafcb30971a90eb3675f4805`. It ran on `llama.cpp` build 10630 (`d222767c7`) with CUDA, full layer offload, flash attention, and a configured 65,536-token context. The server metadata reported 30,697,345,596 parameters and a native 262,144-token training context.

| Prompt tokens | Prompt processing |
|---:|---:|
| 2,048 | 662.50 tok/s |
| 4,096 | 649.55 tok/s |
| 8,192 | 629.67 tok/s |
| 16,384 | 594.78 tok/s |
| 32,768 | 540.34 tok/s |

The three-run 128-token generation baseline averaged **6.796 tok/s**; the sweep's final generation run measured 6.765 tok/s. The managed cold load reached health plus real-inference acceptance in **15 seconds**. Whole-system available memory fell by **39.38 GiB** from the unloaded baseline, leaving **79.42 GiB available** after the 65,536-token server initialized. During direct benchmarking, GPU utilization peaked at **96%** and mean non-zero utilization was **93.46%**. Five warm streaming requests measured **754 ms median TTFT** with a 753–788 ms range. Three subsequent 128-token visible-response checks returned the exact requested text, the service remained active, and its recent journal contained no OOM, CUDA-error, or fatal matches.

The first managed inference check used only 32 output tokens and failed because the model consumed that allowance in hidden reasoning before emitting visible content. Raising the bounded verification allowance to 128 tokens produced the expected visible response. The runtime also warned that the GGUF embeds an outdated Gemma 4 chat template and applied its compatibility workaround; this should be rechecked if the artifact or runtime changes.

## Qwen3.6 35B A3B NVFP4 with Qwen3-Coder-Next also loaded

This September 2026 experiment kept both model services loaded on one GX10, sent the main performance requests one model at a time through a shared OpenAI-compatible gateway, and separately sent one bounded request to each model simultaneously to test stability. Qwen3.6 35B used vLLM with ModelOpt NVFP4, a configured 32,768-token context, and one maximum active sequence. These are deployed-runtime observations, not a coding-quality score or a single-model 35B baseline.

Three identical-text, 128-token requests per model succeeded. After the first request, the two warm Qwen3-Coder-Next Q5_K_M requests had a 55.63 completion-tokens/s median measured over whole-request wall time; the two warm Qwen3.6 35B requests had a 71.83 completion-tokens/s median. Each model tokenized the text differently (4,148 versus 4,509 prompt tokens), and the warm requests may have benefited from prefix caching. These figures therefore show promising short-request service speed, not an apples-to-apples decode or quality ranking. No new swap-in or swap-out was measured during those six short requests.

The unchanged controlled Hermes file-tools fixture passed for Qwen3-Coder-Next Q5_K_M in 33.88 seconds. Hermes rejected Qwen3.6 35B *before inference* because its served 32,768-token context is below Hermes Agent's 64,000-token minimum. Tool-use correctness for 35B remains untested; the rejection does not imply that the model cannot call tools. Raising only the client-reported context would misrepresent the actual server limit.

The memory result limits this deployment further. One simultaneous 256-token request to each model completed without a crash, but the kernel swapped out about 124.9 MiB of pages. A later **sequential** 35B request with 6,034 prompt tokens and 128 completion tokens finished in 2.718 seconds, with 1.044 seconds to the first streamed delta, but swapped out about **147.5 MiB**. The 35B vLLM process held the additional swapped pages; the Qwen3-Coder-Next process showed no swapped pages. Both services remained healthy. The sweep stopped before 16K and 24K prompts, so there is no sustained long-context result.

**Disposition:** Qwen3.6 35B NVFP4 is a promising direct-API experiment but **not an accepted Hermes coding worker in this dual-loaded setup**. The current 32K context is a hard Hermes compatibility blocker, and the measured swap-out fails the desired no-swap operating criterion even when the 35B model is queried alone while Q5 remains loaded. Qwen3-Coder-Next Q5_K_M remains the worker default. A later 64K serving experiment would need an explicit memory plan and the unchanged Hermes fixture before reconsideration.

## Current choice

The two earlier Qwen models and DeepSeek completed the baseline tool-use task correctly; Gemma did not, and Qwen3.6 35B was blocked before that task began. **Qwen3-Coder-Next Q5_K_M remains the default single-GX10 worker** because it provides the strongest measured operational balance. **DeepSeek V4 Flash is rejected for this worker use case because it is too slow and memory-heavy.** A future quality claim alone does not make it a candidate unless end-to-end speed and headroom also improve materially. Gemma is installed as a separately selectable uncensored chat/quality experiment, but its 6.80 tok/s generation rate and failed path-following acceptance exclude it from worker use until a later runtime/template or model revision passes the unchanged fixture.

## Further single-GX10 capacity experiments

DeepSeek demonstrates that the GX10 can run a worker close to its practical memory ceiling. The goal of further experiments is not to fill all 128 GB, but to find the strongest configuration that preserves enough headroom for the OS, runtime, KV cache, and a 65K context.

DeepSeek V4 Flash 0731 is now benchmarked. It fits, serves an OpenAI-compatible endpoint, and passes the controlled Hermes task, but is unsuitable for our single-GX10 coding worker because of its measured speed and memory cost.

The earlier quant-upgrade candidates were:

1. **Qwen3.5-122B-A10B Q6_K** — a capacity-oriented experiment, but the tested Q5_K_S variant already took 149.23 seconds for the Hermes fixture. A higher quant is not an attractive next worker test without evidence of a substantial coding-quality gain.
2. **Qwen3-Coder-Next Q8_0 or Q6_K** — higher precision than the current Q5_K_M, but no longer a presumed quality upgrade. An independent [Qwen3-Coder-Next quantization ladder](https://www.damenknight.com/mi300x-quant-ladder/) tested all three in the same Aider Polyglot setup and found Q5_K_M 58.7, Q6_K 58.2, and Q8_0 57.8 (pass@2); the differences were within run-to-run noise. That test used different hardware, runtime backend, quantization artifacts, and tasks, so it does not replace a GX10/Hermes comparison. It removes the evidence-based reason to prioritize a larger quant merely for coding quality.

Keep Qwen3-Coder-Next Q5_K_M as the default. If a specific failure suggests quantization damage, compare the same real coding tasks across quants and record quality, end-to-end time, peak unified-memory usage, and GPU utilization. The preferred configuration should leave practical memory headroom rather than merely proving that the model can start.

## Deferred reference — dual-GX10 DeepSeek V4 Flash FP8

This is separate from the completed single-GX10 DeepSeek V4 Flash benchmark above. It is not an active next-model recommendation after the single-box speed rejection. Retain these recipes as historical references if a second GX10 becomes available and a new measured performance case warrants reconsideration. Multiple public dual-DGX-Spark/GB10 implementations have demonstrated the higher-quality model across two 128 GB GB10 machines.

Target: **official/high-quality DeepSeek V4 Flash FP8 across two GX10s using tensor parallelism (TP=2)** rather than the aggressively compressed single-box build. Published dual-Spark results report roughly **38–44 tok/s single-stream**, with substantially higher aggregate throughput under concurrency. One published setup also demonstrates 1M context.

Recipe/reference implementations:

- [elsung/dgx-spark-deepseek-v4-flash](https://github.com/elsung/dgx-spark-deepseek-v4-flash) — dual GB10, official FP8, vLLM TP=2, 200 G QSFP56 RoCE; includes settings, recipes, gotchas and benchmark results.
- [jvr0x/dgx-spark-bench — DeepSeek V4 Flash dual recipe](https://github.com/jvr0x/dgx-spark-bench/tree/main/recipes/deepseek-v4-flash-dspark-dual) — reproducible dual-Spark vLLM profile and benchmark harness; measured 46.9 aggregate tok/s at concurrency 1 and up to 177.8 tok/s at concurrency 12 in its tested configuration.
- [r0b0tlab/deepseek-v4-flash-nvfp4-gb10-benchmark](https://github.com/r0b0tlab/deepseek-v4-flash-nvfp4-gb10-benchmark) — native Blackwell FP8/TP=2 benchmark and reproduction notes, including driver-version performance caveats.
- [marksunner/dgx-spark-ds4-benchmark](https://github.com/marksunner/dgx-spark-ds4-benchmark) — alternative distributed Q4 path using `ds4`; useful as a fallback/reference and for comparing runtime approaches.
- [AmesianX/deepseek-v4-flash-dgx-spark](https://github.com/AmesianX/deepseek-v4-flash-dgx-spark) — battle-tested dual-Spark recipe with vLLM, TP=2 and 200GbE RoCE/RDMA, including troubleshooting for RDMA/NCCL and node consistency.

Implementation plan when the second GX10 is available:

1. Connect the two boxes using the fastest supported direct ConnectX/QSFP link and configure RoCE/RDMA networking.
2. Keep driver, kernel, CUDA/runtime, firmware and serving stack aligned on both nodes.
3. Start from the documented vLLM TP=2 recipe rather than inventing a distributed configuration from scratch.
4. Serve one OpenAI-compatible endpoint so Hermes sees the two physical machines as one model provider.
5. Run the same Hermes tool-use baseline used by the single-GX10 benchmark.
6. Record single-stream generation, prompt processing, TTFT, task wall time, aggregate throughput under concurrency, per-node unified-memory use, GPU utilization and interconnect throughput.
7. Compare the dual-GX10 FP8 result directly with single-GX10 Qwen3-Coder-Next and single-GX10 compressed DeepSeek V4 Flash.

The existing Qwen measurements remain for historical reference even if a later model becomes the preferred worker.

These numbers describe this specific GX10/runtime/configuration and should be treated as empirical baselines rather than general model-performance claims.
