# Hermes process-group timeout coding fixture

Status: **ready as a bounded coding-acceptance fixture**; not yet a long-context compression benchmark.

This fixture freezes a real lifecycle bug in `ai-commands/system/hermes-agents/src/run-installer-with-timeout.py`: the helper starts its command in a new process session, but its timeout and forwarded signals target only the direct child. A child that spawns another process can therefore leave that descendant running after the helper reports a timeout.

The starter is an exact copy of that source on the `codex/gx10-qwen-benchmark` branch as of 2026-09-28. A run stages the starter at a fresh, visible, ignored path under `notes/benchmarks/local-models/runs/`; Coder may edit only the staged copy. The production helper is read-only. The assignment is [`TASK.md`](TASK.md). Run the independent [`verify.py`](verify.py) against the saved candidate after Coder exits. It checks normal exit and inherited streams, invalid timeouts, process-group timeout, and forwarded SIGTERM/SIGINT with a signal-resistant descendant. It creates no files and cleans up its captured process groups. Keep each run's edited file, verifier output, Hermes session ID, model calls, wall time, and process-exit evidence.

The verifier has been checked against three states: the frozen starter fails timeout and both external-signal cases; a partial Coder fix passes timeout but fails both signals; an ignored, reviewed reference candidate passes all six cases. The self-check output is retained under `runs/sc-process-group-reference-2026-09-28/`. For a compression comparison, a relevant reproducible context packet or multi-step session must actually drive a model call past the proposed 32,768-token cap and log a compaction event. Use the same starter, context, assignment, model/server, CLI route, file write scope, turn/process limits, verifier, and correction rule in both arms. Count accepted behavior and process cleanup before comparing speed.

Do not infer a compression benefit from a run that stays below the cap. Do not use a plausible completion message as the verifier result. Restore any staged checkout file and inspect the repository diff after each process exits.

The first verifier-authoring Coder attempt stopped at its outer process deadline. Its partial file used forbidden temporary directories and had a broken generated child script. A smaller focused attempt then returned a verifier whose pipe handling could hang and lose the descendant PID. Its one allowed correction stopped at the outer deadline and left code that changed the CLI contract, wrote under `/tmp`, and put the descendant in another session. All three outputs were rejected; the first and final outputs are retained only as ignored diagnostic artifacts. None was run. Admin authored and self-checked the current independent verifier afterward.

An independent inline PID diagnostic subsequently confirmed the frozen starter's defect without creating a verifier file: after exit 124 and the timeout diagnostic, both an ordinary sleeping descendant and one ignoring SIGTERM remained alive. A staged Coder implementation in ignored `runs/sc-process-group-timeout-2026-09-28-1/` passed both timeout cases after one correction. It **failed the separate external-SIGTERM case**: the direct child exited while a SIGTERM-resistant descendant survived. The diagnostic killed each captured process group afterward. This staged file is partial evidence, not an accepted fixture implementation or a compression benchmark; the production helper remains unchanged.

A later four-run matched prompt pilot used the checked verifier and frozen starter. Two baseline and two clarified assignments all failed timeout, SIGTERM, and SIGINT cleanup. One clarified run hit the 180-second outer limit. The clarified wording did not transfer the recognizer's task-specific gain to this process-lifecycle task. Outputs and exact session IDs are retained in ignored `runs/sc-process-group-prompt-2026-09-28/`; no production file changed.
